**(PPT页：一条时间轴，展示 New Bing -> ChatGPT -> Trae/Agent)**

先讲讲我和 AI 的故事。我相信在座的很多朋友跟我一样，最开始接触 AI 编程，大概是从 GPT-2.5 时代的 New Bing 开始的。
那时候，AI 对我们来说更像是一个**“超级搜索引擎” (Search)**。我们问它问题，它把网上的答案嚼碎了喂给我们。
后来，有了 ChatGPT，它变成了 **“聊天机器人” (Chat)**。我们把一段报错扔进去，它告诉我们怎么改，或者让它帮我们写一个快速排序的函数。这时候，它是一个好老师，但它并不了解我们的整个项目。

而现在，当我们使用 Cursor/Trae 这样的工具时，我感觉进入了 **"Agent" (智能体)** 时代。它不再只是陪聊，它能看见我的整个文件列表，能读懂我的项目结构，甚至能主动帮我修改文件。它从一个“场外顾问”，变成了坐在我旁边的“结对编程伙伴”。
从嘴变成手，甚至是大脑的功能。

## 3:00 - 5:30 | 核心心法：PRD -> Proto -> Dev
**(PPT页：展示核心方法论三角形：PRD（需求） -> Proto（原型） -> Dev（实现）)**

**（核心干货）**
在使用 Trae 开发的过程中，我总结了一套**“三步走”心法**。在这个流程里，我不像是在写代码，更像是在做一个 **产品经理** 和 **架构师**。

**(PPT页：Step 1 - PRD 截图，展示你和 AI 的对话，用自然语言描述业务逻辑)**

**第一步：PRD（需求定义）。**
以前我们写代码，上来就 `npm init`。但在 AI 时代，最重要的是**“把话说清楚”**。
我会直接告诉 Trae：“我要做一个订单查询页，逻辑是：用户输入手机号 -> 后端去云数据库查询 -> 如果有数据，返回状态列表；如果没有，提示未找到。”
你把逻辑理得越顺，AI 写的 Bug 就越少。

**(PPT页：Step 2 - Proto 截图，左边是代码，右边是界面)**

**第二步：Proto（原型设计）。**
这一步最爽。我不需要学 Figma，我直接让 AI 给我“画”代码。
我说：“给我一个二次元风格的查询框，背景要粉色，带一点圆角，查询结果用时间轴展示。”
Trae 啪啪啪生成 WXML 和 WXSS，一运行，界面就出来了。不好看？直接说：“把按钮改大一点，颜色再深一点。”这种即时反馈感非常强。

**(PPT页：Step 3 - Dev 截图，展示 Trae 的多文件编辑界面)**

**第三步：Dev（功能实现）。**
这是 Agent 最强的地方。当我要对接真实数据时，我需要改云函数、改前端逻辑、改配置文件。
以前用 Chat 模式，我得一个个文件复制粘贴。但在 Trae 里，它分析完我的需求后，会直接列出：“我需要修改 `index.js`，增加 `cloudfunction`，还要改 `app.json`。”
我只要点一下“Apply”，它就帮我把这三个文件都改好了。这种连贯性，是以前体验不到的。

## 7:30 - 9:00 | 避坑与进阶：人机对齐漏斗
**(PPT页：漏斗模型图解 - 倒三角形，Layer 1 自然语言 -> Layer 2 视觉锚定 -> Layer 3 生产代码)**

**（深度思考）**
当然，过程也不是一帆风顺的。很多人问我：“为什么 AI 总是不懂我的需求？”
这里我想分享一个我总结的**“人机对齐漏斗模型” (The Alignment Funnel)**，这是解决 AI 听不懂人话的关键。

大家看这个倒三角：
*   **最上面是“宽入口”**：这是我们的**自然语言**。比如我说“做一个大气的界面”。这对 AI 来说太模糊了，是 High Context 的。直接给这种指令，AI 只能瞎猜，这就容易产生“幻觉”。
*   **中间是“过滤层”**：这是**视觉锚定**。为了不让 AI 瞎猜，我会给它参考图，或者让它先生成一个简单的 HTML 原型。就像装修房子，先看效果图，再动工。
*   **最下面是“窄出口”**：只有经过了中间层的确认，我们才让 AI 去写最终的**生产代码** (Low Context)。

**所以，不要试图用一句话让 AI 完成整个 App。**
通过这个漏斗，我们把模糊的需求层层过滤，最后得到的代码才是精准可用的。这也是为什么我前面强调 **PRD -> Proto -> Dev** 这个顺序的原因。
